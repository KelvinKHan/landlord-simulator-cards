# 房东模拟器：项目整体理解

依据：Z5.20 原始导出、全部组件源码、已核查的插件接口。更新于 2026-09-07。这里描述已存在的设计与实现，不添加新需求。作者已取消大富翁方向，当前工作止于理解，不展开修复或重构。

## 核心玩法与分工

玩家作为房东，安排公寓空间，主动招募租客，确认入住，再与有独立性格、关系和生活的租客持续互动。建造、日常、手机聊天、外出和世界观内容共同支撑这段持续发展的生活。人物不会只因为住进公寓就失去独立意志；W04 规定人格独立，W14 规定人物的知情范围。

一次主线操作经过：**玩家提出意图 → 世界书提供规则与已有事实 → 主模型写剧情和变量补丁 → MVU 处理状态 → 界面读取并呈现 → 新状态回到下一轮提示词。**

公寓按钮大多把自然语言指令填到输入框。玩家发送后，建造或退租等动作才交给模型处理。基建规则要求瞬间完成、不描写施工；规则写在提示词中，程序提供的强制校验只是其中一部分。因此理解一个功能需要同时看按钮发了什么、哪条世界书被触发、补丁写到哪里，以及谁刷新画面。依据：[操作闭环](flows.md)、[W01–W04](worldbooks.md)、[S00/S01/S04](scripts.md)。

## 人物有四层记录

| 层次 | 含义与保存位置 | 谁改变它 |
| --- | --- | --- |
| 固定档案 | 人物的基本信息、性格、背景、兴趣、习惯；保存在聊天绑定世界书，条目名为姓名 | 档案卡保存按钮或工坊导入 |
| 长期变化 | 经历造成的持续变化；世界书条目 `[租客动态]姓名` | 租客分析脚本把固定档案、旧动态和近期剧情交给副模型分析后写入 |
| 即时状态 | 年龄、外貌、职业、性格、状态、内心、关系；消息的 MVU `租客列表` | 主模型的变量补丁 |
| 手机经历 | 手机数据库保存完整会话；`[租客微信]…` 世界书保存截断摘要 | 手机生成模块写消息，同步模块写摘要 |

这些记录有不同的更新时机。分析脚本写了长期变化，并不等于 MVU 的内心已经变化；手机显示了回复，也不等于主模型已经收到这段记忆。主模型通过世界书和变量宏读取它们，手机副模型则由自己的脚本挑选上下文。

**姓名是多个系统共同使用的关联键。** 租客字典、房间住户、档案条目、动态条目和手机联系人依赖名字找到同一个人。房间字典的键与房间显示名称也需要区分，入住指令使用实际房间键。来源：[S04/S09/S11/S12](scripts.md)、[R04](regex.md)。

“住户”表示长期住在哪间卧室；人在厨房、花园或外地的临时位置由剧情描述。关系是每位租客各自持有的“对象名 → 关系描述”，不是自动对称的好感数值。公寓的玩家关系视图会把不在租客名单内的关系对象归为玩家，这是 S04 当前的显示判断，不是新增的人物设定规则。

## 新游戏与招募是两条入口

初始公寓结构来自 W00 `[InitVar]`。它虽在世界书里关闭，MVU 仍按初始化条目读取；无需让它作为普通提示词发送。世界观来自单独的设定条目或工坊注入，开场白负责初次情节与补丁，这三者各有职责。

默认开场是使用说明。两个备用开场分别提供空公寓与六租客情境；六租客开场直接增加房间和人物变量，没有同时创建六份固定档案。因此不能把“变量里已有角色”理解成完整走过招募与存档流程。详见 [初始化与开场](worldbooks.md)。

普通招募的完整交接是：

1. 公寓发出规定招募短语，W07 要求五位候选人，用 `<companion>` 输出。
2. R03 或 S22 显示候选人，允许选一至两位；选择消息中的“作为新租客”触发 W06。
3. W06 要求 `<TenantLore>` 固定档案，R04 或 S22 提供编辑、保存和办理入住。
4. 保存把资料写进聊天世界书；办理入住另发消息，主模型添加租客并更新卧室住户。

候选展示、档案生成、档案保存、正式入住是四个不同阶段。工坊角色则先直接保存现成档案，再填写入住指令，绕过候选生成。工坊“应用预设”中的单纯资料导入又不等同于正式入住。详见 [招募流程](flows.md)。

## 世界书、正则和脚本怎样接上

| 世界书组合 | 提供什么 | 对应脚本或正则 |
| --- | --- | --- |
| W00–W04 | 初值、更新规则、补丁格式、当前状态、基建与招募基本约束 | S00/S01 处理 MVU；S04 公寓；R00–R02 处理占位符与更新段显示/隐藏 |
| W05 | 默认世界观原始资料，目前关闭 | S23 工坊按操作应用世界观、附加世界书和开场 |
| W06/W07 | 选人后的档案格式、招募候选格式与触发词 | R03/R04 或 S22 显示交互；S04 提供招募入口 |
| W08–W11 | 群聊、搜索记录、日记、直播四种正文附加形式，目前关闭 | R05–R08 或 S22 显示，不写入真实手机消息库 |
| W12/W15 | 新闻和天气变量进入主提示词的入口 | S06/S20 或 S29 生成/展示新闻；S19 计算天气 |
| W13 | 世界旅行指令与坐标的解释规则 | S18 生成匹配短语；S16 城市地图的短语不匹配它 |
| W14 | 主模型扮演人物时的知识边界 | 手机、分析和新闻副模型有独立提示词，是否继承需逐条看其取材 |

正则同时承担“读者看什么”与“历史提示词保留什么”，其中档案和候选替换还含交互脚本。MVU 读取原始更新段；显示面板本身不负责执行补丁。当前还启用了 S22，它另行读取原始消息并重绘候选、档案和 DLC，因此存在两套显示入口。不能只看某条正则就判断最终画面。详见 [九条正则](regex.md)。

这份导出没有 EJS `<%` 模板代码。当前状态注入使用酒馆助手的消息变量宏，新闻天气使用酒馆聊天变量宏。EJS 是以后可能用到的能力，现有主线不能据此推定依赖它。

## 手机、环境和工坊在主线中的位置

原版手机由 S06 提供容器和副 API 设置，S07 保存会话，S11 生成群聊/私聊，S13 提供聊天界面，S12 把截断记录写回世界书。正文可以通过摘要承接手机经历；正文剧情和 DLC 群聊不会自动变成手机数据库里的消息。

租客分析 S09 经 S08 队列更新长期档案，S14 是查看和控制入口，S10 展示队列。新闻也是副模型生成的游戏内内容；天气来自日期算法；地图把目的地变成剧情输入。它们为生活提供上下文，数据来源和更新时间各不相同。音乐 S17 是媒体播放；欧欧聊天 S21 有独立人设和历史，未接入租客消息库及正文摘要。

工坊 S23 保存和应用角色、房间、世界观、表情包。不同按钮有不同副作用：角色可以存档后招募，房间填写建造指令，世界观可写入世界书并替换第 0 条开场。工坊不是单纯的素材预览窗，也不是保存全部游戏进度的工具。

悬浮菜单 S02 管理入口，S03 切换脚本组合，S15 提供调试观察。S05 是关闭的示例。以上模块的输入、输出、存储及生命周期详见 [脚本表](scripts.md)。

## 两套实现与理解边界

作者已明确：二改版是其他创作者制作的二创，两套版本均需保留，让玩家二选一。这个选择不要求合并两套实现；是否支持已有聊天中途无缝切换及完整记录迁移，目前尚未作为要求提出。世界书规则冲突的取舍留待作者考虑，实际酒馆配置暂不展开。

当前导出主要启用原版公寓和手机，并启用 S22 美化。关闭的 S25–S29 构成另一套 AptSystem：自身的公寓底座、分析、通讯录、音乐与报社。它们共享部分 MVU 和世界书命名，却有独立设置与手机数据库；切换开关不代表数据已经迁移。后续谈改动时必须明确落在哪套实现，不能把两套能力合并当成当前同时存在的功能。

大富翁 S24 及专属玩法已退出方向。原卡的开关预设和共享 schema 仍有旧引用，这是保留原始导出的事实，不是继续开发它的计划。

已经完成的理解覆盖全部世界书、正则、脚本及其主链路、存储边界和触发关系；语法、字段与部分接口行为经过离线核验。尚未在用户实际酒馆环境中运行，因此版本差异、加载时序、模型遵守格式的稳定性和最终界面表现仍属于运行待验。具体记录见 [核验结果](verification.md)。
