# 配合问题、证据和处理顺序

这次交付是理解与诊断，未修改原卡、插件启停或业务逻辑。以下问题有不同证据强度：静态确认说明代码确实如此；离线复现说明隔离样例已重现；运行待验说明还取决于实际插件或浏览器状态。

2026-09-07 范围更新：作者要求先完整理解项目，暂不进入修复。下文“处理”是先前记录的技术备选，不是当前执行计划；大富翁专属问题（包括 F19）退出后续工作，共享字段问题只在剩余模块中考虑。

## 第一组：变量和存档的正确性

### F01：最外层 Zod 一致性检查可能根本没有执行

**当前 CDN 实现已确认，Zod 4.1.11 最小样例已复现。** S01:92–129 的 superRefine 检查租客与房间双向对应；但当前 registerMvuSchema 对顶层 ZodObject 重新取 shape 创建 looseObject，没有保留原对象的 refine。最小实验中原 schema 拒绝的无效数据被重建 schema 接受。嵌套 RoomSchema 的 refine 仍保留，不应把它误说为“所有验证失效”。依据：[辅助库源码](https://github.com/StageDog/tavern_resource/blob/dee97e8c3e24e1e75efe21141743e4b5c0af776e/util/mvu_zod.ts#L3)，此次实际 CDN 快照摘要见 verification.md。

影响：源代码看似防止“幽灵住户”和“无房租客”，实际保障可能不存在。实际浏览器加载的是哪一版，还需运行时确认。

处理：固定依赖并确认 schema 注册方式，明确最终状态的校验时机。不能仅把 superRefine 恢复：辅助库逐条验证补丁，先加租客或先改房间都可能在中间状态失败；应设计组合操作/事务边界。分基地租客也需纳入住宿一致性，当前顶层检查只认主公寓房间。

### F02：嵌套字段会被 schema 丢弃，扩展玩法却在写这些字段

**字段缺口静态确认；Zod 嵌套未知字段剔除已复现。** S24:4333 把 activeBuffs 写进大富翁，另有尺度等设置；S01:63–82 没有定义这些字段。S25/S28/S29 读取世界.天气，S01 世界对象未声明，W15 又使用独立的 phone_weather。

影响：脚本直接写后可能暂时可见，下一次模型补丁经 Zod 整体解析时被剔除，表现为增益或设置丢失。用户/资金属于未知**顶层**路径，当前 looseObject 会保留，不能和未知嵌套字段混为一谈。

处理：建立唯一字段契约，补齐需要持久化的字段，区分设置与游戏状态，验证“脚本写入 → AI 更新 → 刷新 → 切聊天再回来”的完整周期。

### F03：手机同步缓存了聊天世界书，却没有按聊天失效

**静态确认，跨聊天影响需在实际生命周期中验证。** S12:336–370 首次获得 WORLDBOOK_NAME 后始终复用；S27:589–612 同样如此。未找到按 chatId 重置该缓存的代码。仅 ChatDB 打开时改变 currentChatId 不会重置它。

影响：如果同一脚本实例跨聊天存活，B 聊天内容可能写入 A 世界书。旁路分析/新闻任务也未绑定提交时的 chatId，切换后取上下文或写回可能落入另一个聊天。

处理：异步任务携带 chatId、目标世界书、来源消息/分支；切换时取消或隔离旧任务，完成时校验归属。不要通过重新加载整个页面掩盖数据归属问题。

### F04：同步失败可能仍显示成功，撤回空会话会留下旧记忆

**静态确认。** S12:125–172、S27:471–497：忙时直接返回 false；updateChatLore 返回 false 不阻止标记 syncedToLore；没有消息时直接成功返回，而不是删除该会话旧条目。截断摘要后也给读取到的全部消息标同步。

影响：手机显示与正文记忆不一致，撤回最后一条消息后主模型仍可能读到旧内容。S27 的删除成功通知发生在异步同步真正完成前。

处理：每会话排队/合并最新同步请求，只有世界书写成功才更新标记；空会话明确删除对应条目；同步状态应记录摘要覆盖范围。验证 API 失败、同时两会话同步、撤回全部与重启。

### F05：覆盖导入前没有完整校验备份

**静态确认。** S07 importData 与 S27 对应实现先按 version 判断，非 merge 会清当前聊天，再遍历 conversations/messages 导入。结构错误可能在清除后才触发。

处理：先解析与校验全部数据和引用关系，再备份当前记录，最后在完整事务内替换。不要用真实聊天作为损坏备份测试对象。

## 第二组：当前启用链路的协议问题

### F06：R02 会吞掉两个更新块之间的正文

**离线复现。** `前<UpdateVariable>一</UpdateVariable>中间正文<UpdateVariable>二</UpdateVariable>后` 被过滤为“前后”。原始消息没有被删除，但下一次主模型以及使用此过滤的副模型会缺失中间内容。

处理：按照明确的完整块与未闭合块协议分别过滤，覆盖大小写、多块、跨行、只出现开标签等样例；同时确认不会把 XML 样例或叙述中的标记误判成真实更新块。

### F07：两个渲染器重复接管同一组标签

**静态确认，覆盖时序运行待验。** R03/R04 内有候选人和档案动作；S22 再从原文生成相同功能，直接重写消息 DOM。解析宽松程度、父窗口查找、按钮状态和可处理深度不一致。

S22:1257–1276 同时处理“消息已渲染”和“收到消息”：前者经过 300ms 合并队列，后者 500ms 后强制重绘，未共享同一条调度路径。强制重绘从原始消息重建 HTML，再于 S22:1170 替换 DOM；已选候选、未保存编辑和按钮禁用状态未在此重建过程中回填。因此这是具体的状态衔接缺口，最终出现次数取决于事件时序；不能据此直接断言每次操作都会重复发送，或原始消息被改写。

处理：确定唯一的标签解析和业务动作来源；其他渲染器只负责外观。修复前至少分别验收 S22 开/关、超过 renderDepth、重生成/编辑/刷新以及两个 TenantLore 同消息。

补充：S22 的 CSS 清理规则较宽，且部分模型文本直接进入 HTML；清理应只针对已识别结构，模型/用户内容在插入 DOM 前应转义或限定可用标签。

### F08：档案保存、入住与名字关联没有强制约束

**静态确认。** 保存与入住按钮独立，候选按钮却叫“确认入住”。实际人名从正文解析；档案键、MVU 键和住户字符串均靠名字关联。卧室选择读取 S04 的缓存而不是实时 MVU，原版公寓没打开时可能拿不到列表。

处理：区分“选择候选人”“保存档案”“办理入住”，在保存成功后进入下一步；固定人物标识，改名时统一迁移关联；办理入住时读取新鲜状态并重新确认房间条件。不要仅改按钮文案就认为链路已完整。

### F09：世界书存在互相冲突的动作规则

**静态确认。** W06 前后对档案生成时是否推进时间、生成其他租客互动有相反要求；W01 合租迁出描述与 W02 示例不一致；W07 的现代背景默认与工坊自定义世界观缺少明确优先级；最终入住消息不再触发 W06 的关键词。

处理：为候选、档案、正式入住、退租四阶段写一致的允许动作；把“正式入住”的执行约束放到该轮必定生效的规则中。保留基建与人物独立性约束，统一同一操作的示例。

### F10：天气没有统一读取世界时间

**静态确认，失败条件明确。** S19:772–879 没有调用 Mvu.getMvuData，先尝试 getvar('世界')，再从某一条最近补丁提取。最近补丁只有时间时，不会继续向前补齐日期；初始“神启元年”无法转换为数字年。预报初次生成还先用宿主真实小时，后续再修正到游戏小时。

影响：公寓能读到日期，不代表天气能读到；小时/日期显示可能滞后。新聊天没有缓存时旧 data 未清空，相同日期条件下还可能沿用。

处理：统一从确定消息分支的 MVU 读取，明确幻想历法到气象日历的转换。测试只改时间、跨日、跨年、幻想年份、同日期换聊天；天气改变目的地的需求需另建位置接口。

### F11：主模型的防全知规则没有覆盖副模型

**静态确认。** W14 只进入主模型；S11/S27 群聊 prompt 包含私聊摘要和人物内心，S06 新闻读取近期剧情，S29 还明确加工秘密线索。DLC 展示给读者的私密片段也不能自动当作人物已知。

处理：按人物与会话定义可见事实，再构造副模型上下文；把 W14 的原则同步到各生成入口。验收使用不敏感的测试秘密，检查不在场角色是否能说出。

### F12：脚本启停和首次加载依赖隐含时序

**静态确认，用户环境运行待验。** 多个模块用 500ms/800ms/2s 等延时加一次性探测；S10 只尝试一次订阅，S09 底部和 init 都会装 watcher，S14 重开增加计时器/监听。S06 卸载会清事件，但原有 singleton、注册表及部分计时器仍可能存活。

具体启动与操作顺序：

| 条件 | 源码行为与定位 | 可以下的结论 |
| --- | --- | --- |
| S09 先完成，S06 后完成 | S09:714–715 自行注册监控；S06:1484–1485 再调用它的 init；S09:86–96 又注册同一类监控，setupFloorWatcher 没有防重标志 | 重复监控的调用路径已确认。是否多发副 API 请求还受分析进度检查约束，不等同于必然重复扣费 |
| S10 的 500ms 定时器触发时 S08 还未导出 | S10:331–341 仅在 AnalysisScheduler 已存在时订阅，没有等待 ready 或重试 | 该启动顺序会使队列窗口错过后续队列更新，调度器本身仍可能正常执行 |
| S08 已接受任务，S06 才调用其 init | S06:1476–1477 调初始化；S08:49–56 清队列、历史和执行状态，没有取消已经在执行的 Promise | 存在任务被重置和执行状态失真的条件路径；不代表每次普通启动都会发生 |
| 玩家在公寓尚未读入最新状态时办理入住 | R04:319、S22:743 调 getApartmentBedrooms；S04:2879 起只读取 cachedMVUData，缓存由 populateDataWithMVU 写入 | 可能拿到空列表或旧住户。这同时涉及操作先后和缓存刷新，并非只调整脚本加载序号就能解决 |
| 脚本被停用、重新启用或更换版本 | S06:1430–1436 清全局 PhoneSystem 的全部监听但保留对象；S09 与 S26 都写 parent.TenantAnalyzer；S26:563–567 的防重标志存于父窗口 | 清理归属和重新绑定存在缺口。是否出现旧回调残留或新回调被清，要按实际卸载时序复现，不能声称玩家二选一就必然同时运行两套 |

参考的酒馆助手源码把运行列表按脚本 ID 排序，各脚本由模块 iframe 装载；列表位置或固定延迟均不能证明依赖已完成初始化。见 [已核查的运行列表](https://github.com/N0VI028/JS-Slash-Runner/blob/8e0f4324e7d051025a333831411f03bd3145fac8/src/store/iframe_runtimes/script.ts)。本轮仅分析导出内部，不要求读取实际用户配置。

S25 的 initCentralState 缺失另见 F15：这是导出内缺少函数的确定问题，调整脚本顺序不会生成这个函数，应与竞态问题分开。

处理：用明确的 ready/注册生命周期、可取消订阅及成对清理；每个脚本需支持启动两次、关闭两次、慢网加载及同卡换聊天。导出列表顺序不能当作依赖已就绪的证明。

### F13：模型文字直接拼接到 slash 命令与 HTML

**静态确认，不代表已经发生泄露或攻击。** 新闻/天气使用 `/setvar …` 加字符串；招募/档案动作也拼接人名。含管道、引号或标签的数据需要转义。S06 保存 API 配置时把 config 写入 console；S15 可能捕获该对象。S06 与 S23 的部分 postMessage 接收未检查来源。

处理：优先用结构化变量 API，统一命令转义和 HTML 转义；调试记录隐藏敏感配置字段；消息桥检查来源窗口及 origin。这次仅阅读源码，没有读取任何实际凭据或浏览器存储。

## 第三组：模式切换、世界观和可选玩法

### F14：“原版”预设与当前导出不是同一套开关

**离线复现。** 切为“原版”关闭 S22、开启 S24；二创版也开启 S24。两种内置预设均没有执行正则重设；世界书未切换。

处理：先保存当前真实开关快照，为每套模式明确脚本、正则、世界书及数据兼容范围；不用泛化的 defaultEnabled=true 意外打开新增实验模块。

### F15：二改版公寓启动调用了未定义函数

**静态确认，AST 核对全卡仅一个引用。** S25:2403 调用 AptSystem.initCentralState()；赋给 AptSystem 的对象没有这个成员，其他 29 个脚本也没有定义。标准独立启用路径会在此抛异常，后面的 MVU 监听与首次渲染无法执行。外部未导出脚本若补过方法，另当别论。

处理：先厘清缺失的中央状态职责，补齐或移除孤立调用，并验证全部二改子模块。仅通过 JavaScript 语法检查无法发现此类错误。

### F16：二改版正文标签和数据桥没有配齐

**静态确认，标签样例已复现。** S26/S29 默认只取 content 标签，而主卡没要求正文包裹；S27 的可选标签过滤也可筛空正文。S28 读世界.天气，但 S19 写 phone_weather 且会被二创模式关闭。S25 不提供 R04 原来依赖的 getApartmentBedrooms。

处理：为二改版制定统一的正文提取协议、日期/天气/卧室查询接口。不要通过随意开启被替代的整个原版公寓来补一个缺失接口。

### F17：两套手机数据库不同，世界书条目却共用名称

**静态确认。** 原版为 TenantChatDB，二改为 AptChatDB；固定/动态/微信世界书的条目名重合。

影响：切换后通讯录历史不自动出现，但另一套留下的摘要仍可能参与正文。同开时又可能相互覆盖摘要和 TenantAnalyzer 全局。

处理：明确迁移/并存策略，提供受验证的导入导出；模式切换时告知数据范围并处理旧摘要，禁止意外双写。

### F18：世界观应用会改旧开场，自动注入函数却没接通

**静态确认。** S23:777–819 直接改第 0 条消息、删旧变量并发假聊天切换事件；823–837 的 wsAutoInjectWorldView 只有定义，没有调用。additionalLore 可使用不带 `[创意世界]` 的名字，清理只按该前缀。

处理：只在明确的新开局/迁移事务中换世界观，先备份开场与变量；通过正式 MVU 初始化/解析 API 处理并等待完成；给附加条目标记归属；把自动注入和聊天作用域接通后再宣称自动继承。

### F19：大富翁分基地招募的姓名交接与渲染冲突

**静态确认，事件先后运行待验。** S24:2993–3014 在 AI 收信后从最后一条消息 DOM 的 textContent 匹配 TenantLore name；R04/S22 渲染后该标签通常已被转换，读取 DOM 不稳定。新增租客不住主公寓，又与 S01 设计的顶层检查冲突。

处理：从确定消息的原始数据取档案标识，并统一提交租客与分基地住户；验证失败恢复、重生成、切聊天和取消，不依赖 DOM 抓取业务数据。

另有 S24 据点等级上限 3/4 混用：OUTPOST_LEVELS 仅 0–3，但并购效果能写 4，getOutpostLevel(4) 回退到 0 级显示/收益。应统一等级上限与结算表。

### F20：预置开场与地图存在小型但明确的接口缺口

**静态确认，地图触发样例已复现。** 六租客开场重复追加“地下一楼”，并未创建六份固定 ChatLore 档案；城市地图句式不触发旅行世界书，而世界地图句式会触发。

处理：开场初始化需可重复运行且不产生重复楼层；为预置人物提供固定档案来源；若城市地图也应使用旅行规则，统一短语或调用结构化动作。

## 建议的修复批次

1. **先保住变量与聊天归属：**固定 MVU/Zod 依赖，定义完整字段和事务验证；修复 ChatLore 的聊天隔离、写入确认、撤回与导入事务。对应 F01–F05。
2. **统一主线协议：**一次完整的建造→候选→档案→入住→退租，消除 W06/W01 冲突，统一两套渲染器动作，并修正 R02。对应 F06–F09。
3. **整理后台模块：**统一世界状态读取、人物知情范围、事件生命周期、请求取消及文本转义。对应 F10–F13。
4. **最后恢复可选模式：**准确开关预设，补齐二改版启动、数据迁移、世界观初始化和分基地链路。对应 F14–F20。

每批都先在独立测试聊天中验收；通过后再形成新版本 JSON/PNG。无需为分析阶段安装全部运行插件或消耗真实副 API 配额。
