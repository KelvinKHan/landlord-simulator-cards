# Z5.20 配合关系梳理

分析日期：2026-09-07。对象为 `originals/房东模拟器Z5.20 (1).json`，SHA-256：`260b248d8cad57b413c19126b2f9aca5d0a819a750b325fd5c7f2aa89f3bbda7`。PNG 内两份角色数据与它一致。

这张卡包含 **16 个世界书条目、9 条正则、30 个酒馆助手脚本，共 55 个组件**。逐项分析包括关闭的条目和脚本；当前启用世界书 10 条、正则 9 条、脚本 23 个。尚未启动实际 SillyTavern，也没有执行卡内脚本、调用副模型或访问用户聊天数据。

## 已建立的整体认识

角色卡的核心内容不在常规的 description、personality、scenario 字段里，这些字段为空。主要规则来自世界书，操作界面来自酒馆助手，数据分别存在消息变量、聊天世界书和浏览器数据库中。手机里的 AI 是单独构造提示词、调用副 API 的另一条生成链路。

最容易混淆的四件事：

1. **档案保存与正式入住是两次操作。** 保存写入聊天世界书；入住还要发消息，让主模型添加租客、更新房间住户，MVU 才会记录。
2. **手机聊天、正文中的 DLC 群聊、主对话是三种不同记录。** 它们不会因为都叫“聊天”就自动同步。手机通过摘要世界书影响后续正文，DLC 群聊只是主模型回复的附加片段。
3. **正则负责呈现或隐藏文本，MVU 负责处理变量。** 看见变量更新面板，只能说明展示链路工作了，不能证明变量已经写入成功。
4. **二改版是另一套应用底座。** 它有独立设置、数据库、调度器和界面；与原版共享部分世界书名称和 MVU 数据，但没有完整迁移桥梁。

## 阅读定位约定

`W00…W15` 是世界书数组顺序，`R00…R08` 是正则数组顺序，`S00…S29` 是导出脚本数组顺序。编号只用于分析，不替换原始 ID。所有条目的精确 JSON Pointer 保存在 inventory.json。

在仓库根目录执行 `python3 tools/inspect_card.py`，会把可读源码解出到 `.local/inspection/`。例如 `S12:240` 表示 `.local/inspection/scripts/S12.js` 的第 240 行；世界书和正则同理。生成目录被 Git 忽略，原卡保持原样。

“静态确认”表示可从这份导出中确定；“离线复现”表示用隔离样例验证过；“运行待验”表示还需确认实际插件版本、配置、事件顺序或模型输出。此分析没有把源码检查等同于酒馆实测通过。
